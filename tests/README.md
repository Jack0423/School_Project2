# 測試

## 執行

```bash
python -m unittest discover -s tests -t .
```

只跑單一模組：

```bash
python -m unittest tests.test_evaluate_photo -v
```

用標準庫的 `unittest` 而非 pytest，**不需要安裝任何額外套件**。

## 這些測試在守什麼

每一項都對應稽核中找到的一個真實缺陷，而不是為了湊覆蓋率。
括號內是稽核報告的編號。

| 檔案 | 守住的行為 |
|---|---|
| `test_model.py` | batch size 為 1 時輸出不可被壓成 0 維（B9）；權重能以 `strict=True` 載入，確保訓練與推論共用同一份架構定義（B6） |
| `test_transforms.py` | 推論與驗證必須使用完全相同的前處理（B7）。前處理若改回 `Resize((224,224))` 壓扁長寬比，技術模型的 SRCC 會少 0.0317 |
| `test_image_loading.py` | RAW 檔依副檔名分流給 rawpy，不可讓 PIL 讀到內嵌縮圖（B1、B2）；`image=` 參數的格式驗證 |
| `test_evaluate_photo.py` | 回傳格式合約（前台依賴）；分數必須落在 0–100（A5）；失敗原因要能分辨根因（A4）；狀態只由技術分決定、量測結果不參與（丙案） |
| `test_technical_analysis.py` | 分析不可自己從硬碟讀檔（B3）；小於分析寬度的影像不可被放大（B19）；雜訊必須在原始解析度上估計（B11） |
| `test_startup_guards.py` | 缺少權重必須明確失敗，絕不可產生任何分數（A1）；`split_data.py` 重複執行要被擋下（B20） |

## 設計上的兩個取捨

**資料缺席時跳過而非失敗。**
`data/` 與 `*.pth` 都在 `.gitignore` 內，換一台機器不會有這些檔案。
若這種情況直接失敗，整份測試就會變成「反正一定紅的」而被忽略。
需要真實資料的測試會標記 skip 並說明缺什麼。

**盡量用合成影像。**
`_util.make_image()` 能精確控制要測的性質（銳利／模糊／過曝／死黑／雜訊），
測試因此不依賴任何被 gitignore 的資料，也不會因為換了照片就飄。

## 這份測試自己驗證過

寫完後做了變異測試：把已修好的 11 個 bug 逐一植回程式碼，確認測試會失敗。

**11/11 全部被攔截。** 過程中抓到自己兩個盲點並修正：

- 測 B19 用的合成影像太銳利（清晰度 65,000，門檻只有 100），
  即使被放大 4 倍仍遠高於門檻，bug 存在也測不出來。
  已改用銳利度接近真實照片的影像（原生約 470、放大後約 28）。
- 測「細項分析不受閘門控制」的斷言被包在 `if` 裡，
  條件不成立時整條測試形同虛設。已改為直接注入固定高分的模型，
  強制製造出「技術分很高但影像確實有問題」的情境。

新增測試後值得重跑一次變異測試，確認新測試真的有攔截能力。
